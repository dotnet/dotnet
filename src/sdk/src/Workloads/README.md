# Emscripten package inputs

Raw Emscripten toolchain packages have a version independent of the runtime and
SDK. Manifest generation and Windows workload packaging share the selection in
[`Emscripten.props`](Emscripten.props) and the validation in
[`Emscripten.targets`](Emscripten.targets).

## 1xx selection and publication

With `DotNet1xxWorkloadManifestVersion` empty, `EmscriptenPackageVersion` is the
standalone producer's `MicrosoftNETRuntimeEmscriptenInternalPackageVersion`.
The current Emscripten manifest is generated locally and uses this version for
its raw SDK, Cache, Node, and Python pack references. Its own package/version
remains SDK/workload-versioned. Historical manifests retain their existing pins.

[`manifest-packages.csproj`](Manifests/manifest-packages.csproj) also references
[`Microsoft.NET.Sdk.Emscripten.Version.Internal.proj`](EmscriptenVersion/Microsoft.NET.Sdk.Emscripten.Version.Internal.proj)
in 1xx. This is the existing redist and workload build/restore/pack traversal,
not a separate optional pack command. `GeneratePackageOnBuild` also produces the
marker on Build. `LayoutBuiltinManifests` only lays out manifests, not the marker.
The producer selects `MicrosoftNETRuntimeEmscriptenInternalPackageVersion` directly
and imports `Emscripten.targets` for shared input/release validation. It does not
import consumer `Emscripten.props`, so it cannot reference its own package.
The conditional project reference excludes the producer from upstack restore,
build, and pack traversal.

**Marker contract:** `Microsoft.NET.Sdk.Emscripten.Version.Internal` is a non-shipping
transport package whose package version **is the selected raw emsdk package
version**, not the SDK or runtime version. `data/EmscriptenVersion.txt` contains
the package-ID family (`EmscriptenVersionCurrent`, currently `6.0.2`).
The generated file is packed through a `None` item with `Pack="true"` and
`PackagePath="data"`, using standard NuGet/Arcade nuspec generation and repository
provenance. The version and family are the transport contract, not a byte-identical
package across SDK builds. A family change requires a new toolchain release/version;
never overwrite a marker with different family data.

The marker goes to `artifacts/packages/<Configuration>/NonShipping`.
[`eng/Publishing.props`](../../eng/Publishing.props) explicitly gives it
`External` artifact visibility for the standard Arcade/VMR asset-manifest and
dependency-flow publication path. This does not make it a public workload pack
or require publication to NuGet.org.

## Upstack consumption

With `DotNet1xxWorkloadManifestVersion` nonempty, `EmscriptenPackageVersion` comes
only from `MicrosoftNETSdkEmscriptenVersionInternalPackageVersion`, generated by normal
dependency flow for the SDK-produced marker. There is no fallback to the branch's
standalone emsdk pin or to the runtime version. The VMR's
[`repo-projects/sdk.proj`](../../../../repo-projects/sdk.proj) passes this property
into the separate SDK process along with the existing 1xx version properties.

The current manifest and VS insertion restore a private, content-only reference
to the marker at that version. Before manifest generation or installer staging,
the build verifies that its family matches `EmscriptenVersionCurrent`. Missing
version, missing restored marker, and mismatched family are explicit errors.
This requires upstack dependency metadata to select the marker from the **same
1xx SDK build** as the workload set. Do not independently advance the marker.

Manifests are still generated locally, like 10.0, with the existing
`DotNet1xxWorkloadManifestVersion` package/version override. No selected-manifest
`PackageDownload` or copy path is used. Upstack does not produce a new marker.
Publication marks any retained marker output `Internal` in upstack, like reused
manifest packages, so it is not republished as a new SDK asset.

## Windows workload MSI modes

[`VSInsertion/workloads.csproj`](VSInsertion/workloads.csproj) preserves the
existing `DownloadWorkloadMsis` modes and SDK-owned MSI generation cadence:

| Mode | Acquisition and staging |
| --- | --- |
| `DownloadWorkloadMsis != true` | Restore raw runtime packs at the runtime version and raw Emscripten packs at `EmscriptenPackageVersion`; stage them for the existing SDK MSI/SWIX generation. |
| `DownloadWorkloadMsis == true` | Restore and stage runtime payload MSIs at `DotNet1xxRuntimeVersion`, Emscripten payload MSIs at `EmscriptenPackageVersion`, and manifest MSIs at `DotNet1xxWorkloadManifestVersion`. Existing MSI/SWIX generation remains disabled in this mode. |

All eight required current Windows raw Emscripten packs must exist before raw
staging. The existing payload-MSI contract uses the corresponding raw pack's
version; it is not inferred from runtime or manifest versions.

## Stabilization and rollout

`Emscripten.Internal` is always prerelease. Validation rejects an effective
prerelease Emscripten version when the SDK label is `rtm`, `servicing`, or
`hotfix`, including upstack marker consumption and MSI restore. Stable
Emscripten versions are accepted; never synthesize one by stripping a suffix.

Before stabilization, emsdk must expose a stable package-version property for
the current family (historically the
`Microsoft.NET.Runtime.Emscripten.3.1.56.Cache.win-x64.Msi.x64` property).
Change selection in both consumer `Emscripten.props` and the marker producer using
`EmscriptenVersionCurrent`; manifest
references, marker production, raw acquisition/staging, and MSI downloads must
advance together. Remove the temporary guard only after that transition.

This implementation does not change dependency subscriptions, standalone
producer/promotion configuration, or checked-in SDK dependency pins.
After the first real marker is published, register it in the consuming upstack
branch's dependency metadata so automation generates
`MicrosoftNETSdkEmscriptenVersionInternalPackageVersion`. No unavailable marker package
or stable producer property is fabricated here.
